# 速度、审核与真人反馈落地方案

状态：已确认的开发方案，尚不代表以下能力全部实现。后续在 `codex/next-iteration` 分支实施和验证，稳定主线保持不变。

## 1. 目标

当前版本的核心流程已经具备：导师 Agent 组织讲解或产物，新手模拟 Agent 检查是否容易理解，来源核验 Agent 检查事实和证据，调度器负责顺序、预算、取消、恢复和记录。本方案不删除这条闭环，而是把它改成适合日常使用的分级流程：常见任务更快交付，重大错误仍然阻断，失败后可以继续修订。

目标是让用户在大多数普通任务中一次得到可用结果，同时让医学事实、实验对照、图表含义、研究结论和方案可行性保持可靠。

交付原则：内部严格，外部自然。用户看到连贯的讲解和可用的成果，次要审核意见留在后台；涉及主要结论的必要科学边界仍在相关内容中准确表达。减少防御性写作不等于隐藏实质不确定性。

## 2. 用户流程分级

### 2.1 普通交付模式

普通带读、一般的 PPT 和初步研究方案采用轻量流程：

1. 调度器读取已确认的论文文本、图表索引、来源指纹和用户要求。
2. 可并行的工作同时进行，例如图表清单、术语清单和证据定位。
3. 导师 Agent 生成初稿。
4. 新手 Agent 和来源核验 Agent 只检查与本次任务有关的关键部分。
5. 没有重大问题就交付。次要问题只在内部记录，默认不展示提示、警告标签或审核清单，也不因这些问题反复打回。

普通模式不要求每个段落都完整执行三 Agent 串行闭环，也不重复检查已经确认且未变化的来源。

### 2.2 严格模式

在线检查范围根据实际任务调整。精读和组会汇报本身是常见任务，不自动触发全篇反复重审；用户要求逐图逐表核对时覆盖指定范围，核心证据不稳定或方案用途需要更完整检查时增加相应检查。必要时保留导师→新手→核验→导师局部修订→复核流程，并记录阻断问题。扩大检查范围不改变次要审核意见默认隐藏的规则。

### 2.3 审核结果分级

审核结果不再只有“通过”或“打回”：

1. 阻断错误：来源不存在、数字或方向错误、把假设说成结果、虚构图表、缺少决定性对照、研究方案遗漏关键可行性或安全条件。先尝试有界的局部修订；仍不能解决时才说明具体障碍，请用户补充材料或修改要求，不交付含该重大错误的最终成果。
2. 次要问题：不影响主要结论和理解的引用粒度、局部解释完整性或措辞问题。内部记录，默认不提示用户、不阻断交付。分类以实际影响为准；“创新表述”或“术语”问题一旦构成实质误导，也必须升级处理。
3. 编辑建议：版式、措辞、段落长短、讲稿节奏。能直接改善的由导师融入正文或页面，不向用户罗列审核意见，不为微小润色反复调用模型。影响阅读的严重排版缺陷不能当作次要美化问题忽略。

审核 Agent 应返回具体位置、问题类型、证据和建议动作。只涉及一个页面或一段文字时，调度器只重做局部，不重生成整份成果。

### 2.4 用户可见内容

1. 带读先说明背景和研究问题，顺着论文讲实验、图表、结果和推理；关键处展开，已掌握的基础适当简略，配合小标题、原文对照和选句追问。
2. PPT 保持清晰的视觉层级、图文布局和证据主线，讲稿单独提供；研究方案把目标、分组、对照、终点和条件写清楚。三类产物均不夹带角色评语、内部问题编号或修订过程。
3. 用户问“可靠吗”“为什么这样判断”“有什么不足”时，依据当前产物版本展开相关来源和判断，避免直接粘贴内部审核日志。
4. 会改变结论适用范围的条件、证据不足或探索性性质，首次交付时就在相关位置简洁说明一次，不能等用户质疑才补充。论文局限本来就是教学或汇报内容，不应因隐藏审核意见而删去。

### 2.5 角色与调度

导师负责教学组织、成果生成与修订；新手负责暴露理解断点和检验是否能使用所学；核验角色负责事实、来源、图表及推理检查。调度器管理检查范围、版本、依赖、预算、取消和恢复。核验意见也须有证据，不能仅因审核角色提出疑问就认定原稿错误；需要先区分原文确实缺失、材料未传入和无依据的额外要求。

## 3. 速度优化

1. 证据缓存：论文版本、图表索引、已核对术语和来源摘录按来源指纹缓存。论文未变化时不重复解析。
2. 并行准备：文本分段、图表识别、来源索引和用户要求整理并行运行；只有依赖前一步结果的生成阶段保持顺序。
3. 有界核验：普通任务只核验影响当前结论的来源；严格任务才扩展到全篇和全图表。
4. 局部修订：审核返回页面、段落或结论编号，修订只覆盖相关单元，并重新检查受影响证据。
5. 有限续接：网络或上游模型中断时，优先复用已保存阶段；提供方支持续接时才续接。仅对明确失败且可安全重试的请求设置有界重试，不把未知结果自动重发。真实发生的调用及费用全部记账，不承诺重试免费。
6. 可见进度：提供简洁的进行状态和必要的等待反馈，不向用户堆叠内部审核细节；保留“取消后重试”和“编辑要求”入口。

缓存复用须匹配来源、任务要求、Skill、模型配置及产物版本；局部修订后检查受影响的图表、讲稿和上下文一致性。内部迭代可并行独立任务，但新手不能提前看到核验答案，修改后的产物不能沿用旧版通过结论。

速度优化的原则是减少重复工作，而不是删掉决定可靠性的步骤。

## 4. 失败与恢复

系统将失败分为四类：

1. 网络或模型连接失败：保留输入、已完成的 Agent 结果和调用记录，提供有限重试。
2. 内容核验失败：保留初稿和审核意见，进入局部修订，不丢失用户要求。
3. 材料不足：先检查已有材料与传入范围；关键材料确实缺少时说明具体缺口，允许用户补充后继续。不影响当前任务的缺口保留在内部，不反复打断。
4. 程序错误：保存草稿和错误上下文，允许恢复或重新开始，不生成伪造的成功结果。

用户看到的提示应说明“发生了什么、已有内容在哪里、下一步能做什么”，而不是只显示“生成失败”。

## 5. Skill 训练与内部迭代

Skill 训练继续采用“小样本定位问题、完整论文检查连贯性、跨功能验证迁移”的组合：

1. 小样本测试术语解释、图表读取、对照识别、来源绑定和失败恢复。
2. 完整论文测试带读主线、PPT 页面与讲稿、研究方案的完整性。
3. 三类产物交叉检查背景、实验设计、对照、结果、局限和来源是否一致，但不能用产物互相一致替代原文核验。
4. 模拟新手使用 PPT 或研究方案完成任务，暴露理解断点；导师补教后，再换条件验证迁移。
5. 只有在候选相对基线没有退步、阻断错误下降且迁移条件通过时，才发布新的 Skill 版本。

内部迭代始终严格执行完整审核标准。并行、缓存、局部修订和阶段复用只减少等待，不减少导师、新手、来源核验、交叉验证或迁移验证的必要检查；内部候选不能因为“用户模式可交付警告”就算通过。在线交付才按上面的分级审核执行。训练记录必须保留模型、材料、版本、预算、失败类型和最终决定，不能把一次成功样本直接当成 Skill 已经普遍变好。

内部报告完整保留细小问题、修订前后差异和未通过项，不因前台隐藏意见而删除记录。工程提速与质量门槛分别评估：不通过降低评分阈值、跳过失败样本或减少必要检查来宣称迭代成功。流程跑完、质量通过和候选获准上线分别记录。

## 6. 真人反馈回流

用户在其他 Agent 上阅读论文、调整讲解、修改 PPT 或打磨研究方案后形成的记录非常有价值。它们不是“随口意见”，而是能帮助训练 Skill 的真实使用信号，但需要结构化整理后才能安全使用。

建议每条反馈尽量包含：

1. 任务类型：带读、图表解释、PPT、研究方案或术语。
2. 原始要求和原回答片段。
3. 用户做了什么修改，为什么修改。
4. 修改后的理想表达或页面效果。
5. 问题类型：事实错误、证据不足、讲解难懂、顺序不佳、过于冗长、排版问题或审核过严。
6. 论文页码、图表或来源位置；没有来源时标记为个人偏好。
7. 这条反馈适用于所有论文，还是只适用于某一篇论文。

可以直接提供聊天记录、前后版本、截图、PPT 页面或研究方案草稿。我会先把它们整理成“偏好”“可复用规则”“案例测试”“待验证假设”四类，再进入小样本回放；不会把单次个人偏好直接改成全局规则，也不会把未经核对的内容写进 Skill。

不要求用户为了反馈额外填写完整表单。其他 Agent 整理出的 Skill、Markdown 或案例包也可作为候选输入，最好附原始例子与修改理由；缺少信息时先标记待验证。导入前移除密钥和无关个人信息，私人反馈默认保存在本地，不随代码公开。训练样本与留出测试分开，避免只学会重复用户改好的答案。

## 7. 第一阶段实施顺序

1. 先实现审核分级、内部记录与用户正文分离，校准误拦截案例；记录当前耗时、调用次数和失败原因作为比较基线。
2. 再实现来源、图表和术语缓存，以及断线续接。
3. 然后补齐 PPT 与研究方案的局部修订和失败恢复。
4. 最后建立真人反馈导入格式，并用真实反馈跑小样本回放和迁移验证。

每阶段都要通过工程测试、隔离环境真实运行和一次人工抽查后再进入下一阶段。主线保持稳定，所有改动先在开发分支验证。

## 8. 验收重点

1. 只有次要问题的成果正常交付，正文不出现后台审核清单；重大错误仍被修复或阻断，必要科学边界不消失。
2. 用户追问时可以解释当前版本的依据与局限，不引用失效核验结果。
3. 带读、PPT、研究方案分别完成真实生成与适用的导出检查；不把“成功拦截”统计成“成功交付”。
4. 分别统计总耗时、各阶段耗时、实际调用数、首次交付率、修订后交付率、误拦截与重大错误漏检。提高通过率不能以重大错误漏检增加为代价。
5. 断线、取消和局部修订不丢失要求及已完成内容，不重复提交同一任务；来源或产物变化后正确失效缓存。
6. 内部严格基线、跨功能检查和迁移检查保持有效；真实反馈能形成可追溯候选，并通过独立案例验证后再考虑上线。
