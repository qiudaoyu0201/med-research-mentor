# 医研导师：给合作者的项目介绍

你好，这个项目叫 **医研导师（Med Research Mentor）**。它是一个面向医学科研初学者的本地科研学习智能体，核心目标不是简单地“帮用户总结一篇论文”，而是把用户带进论文的研究逻辑里：为什么要做这个问题、研究者怎样把问题转成实验、每个实验验证什么、图表中的证据怎样支撑结论、结论还有哪些边界，以及这些思路如何迁移到自己的课题中。

你可以把它理解成一个结合了论文导师、科研汇报助手和研究方案讨论助手的工作台。用户从一篇 PDF 或一个研究想法开始，系统会帮助他逐步理解、组织和验证，而不是一次性给一大段看完就忘的文字。

## 一、为什么做这个智能体

医学科研新手通常不是没有学习意愿，而是不知道怎样读论文。他们能看到标题、摘要和图，但很难把下面这些问题串起来：

- 论文真正要解决的研究问题是什么？
- 研究背景为什么重要，现有方法缺在哪里？
- 实验设计中的每个分组、对照和测量分别在验证什么？
- 图表的横纵坐标、比较对象、统计量和显著性应该怎么读？
- 结果到底支持了什么，不能支持什么？
- 论文的方法能不能直接迁移到自己的课题？需要补哪些条件？
- 如果要向导师汇报，怎样讲清楚实验思路、证据、创新点和局限？

传统的问答式 AI 往往只给一个看起来完整的总结，却没有持续的教学节奏，也不一定能保证每个结论都回到原文证据。医研导师的设计重点，就是把“解释”“证据”“学习断点”和“下一步”放在同一个闭环里。

## 二、产品的三条主线

### 1. 论文带读

论文带读是主线功能。用户导入一篇医学论文后，系统一般从背景、研究目的和研究价值开始，再沿着论文顺序逐步进入方法、实验、图表、结果、讨论和局限。

每次回答不会只输出一堆文字，而是尽量采用清晰的小标题、短段落、关键词中英对照和来源入口。对于重要图表，系统会解释：

- 图或表想回答什么问题；
- 横轴、纵轴、分组、颜色、符号分别代表什么；
- 哪些比较是关键比较；
- 数据变化说明了什么；
- 统计显著和实际意义分别是什么；
- 这个结果能支持哪一个结论，不能进一步推出什么。

用户可以要求“详细一点”“简略一点”“继续”，也可以引用回答中的某一句进行追问。回答旁边可以打开对应 PDF 页面、图件和原文片段，必要时再请求翻译。系统还会显示当前读到哪里、下一步建议读什么，使对话保持连续。

带读的目标不是让用户背完整论文，而是让用户逐渐形成科研阅读习惯：先抓问题，再看设计；先明确比较关系，再看数据；最后判断证据与结论是否匹配。

### 2. 医学论文汇报 PPT

PPT 是独立生成专区，不要求用户先完成整篇带读。用户可以选一篇已导入的论文，填写页数、汇报对象和侧重点，系统生成适合组会或向导师汇报的 PPT 草案。

PPT 内容通常包括：

- 论文背景与临床/科研价值；
- 研究问题和核心假设；
- 实验设计、研究对象和关键对照；
- 主要结果及图表解读；
- 创新点、局限和可进一步讨论的问题；
- 对自己课题的启发。

生成时会尽量保留原文图件与来源绑定，避免只生成抽象文字。幻灯片中的文字保持可编辑，讲述提示单独生成和导出，不把长讲稿硬塞进 PPT 页面。用户拿到 PPTX 后可以继续修改排版、顺序和表达。

### 3. 研究方案

研究方案功能用于把用户的研究问题、已有线索、条件限制和参考论文整理成一份可以和导师讨论的草案。

它会帮助组织：

- 背景、研究缺口和意义；
- 研究目标与假设；
- 研究对象或实验材料；
- 纳入排除条件；
- 暴露、干预、结局和测量；
- 对照、混杂、偏倚和质量控制；
- 统计分析和样本量确定路径；
- 可行性、伦理、风险与进度；
- 可能结果、创新点和局限。

这里有一个重要原则：没有提供的数据、效应量、设备条件、伦理批准或实验参数，不会被写成已经确定的事实。系统会把它们放在 assumptions、unknowns 或 questions 中，形成下一步需要和导师确认的事项。方案是讨论草案，不是未经验证就可以直接执行的实验 SOP。

## 三、三 Agent 协作设计

项目不是“一个大提示词包办所有事情”，而是由调度器组织三个角色。

### 1. 导师 Agent

导师 Agent 负责主要生成和教学工作：

- 组织论文讲解；
- 解释术语、方法和图表；
- 生成 PPT 和研究方案；
- 根据用户的详细程度和重点调整表达；
- 读取新手反馈和来源核验结果；
- 对关键缺口进行有界修订和补教。

导师 Agent 的重点是把复杂内容讲得连贯、具体、可继续学习，同时保留证据边界。

### 2. 新手模拟 Agent

新手模拟 Agent 不假装自己是专家，而是模拟一个真正刚接触医学科研的学习者去阅读生成结果。它会尝试回答：

- 是否理解研究问题；
- 是否知道实验为什么这样设计；
- 是否看懂比较组和图表；
- 是否能说出结果支持的结论；
- 哪些地方跳步太快或术语没有解释；
- 换一个条件后是否会机械照搬原论文。

它的作用是暴露“作者以为已经讲清楚，但新手实际上没有理解”的断点。

### 3. 来源核验 Agent

来源核验 Agent 对照 PDF、图注、原文片段和已注册来源，检查：

- 事实是否来自提供的论文材料；
- 引文和图件是否绑定正确；
- 是否把相关写成因果；
- 是否把假设、设计建议或可能结果写成论文已经证明的事实；
- 是否漏掉影响结论的关键实验条件、对照或限制；
- PPT、研究方案和带读中的表述是否相互矛盾。

它关注的是证据和边界，不是单纯评价语言是否好看。

### 4. 一个典型闭环

带读中的典型流程是：

```text
用户问题 / 论文材料
        ↓
导师 Agent 生成讲解
        ↓
新手 Agent 试读并指出理解断点
        ↓
来源核验 Agent 检查证据和引用
        ↓
调度器汇总反馈
        ↓
导师 Agent 有界修订或补教
        ↓
新手复读 + 来源复核
        ↓
继续下一阅读单元
```

普通局部追问不一定调用完整链路，调度器会根据任务选择必要角色，以控制成本和响应速度。关键学习任务、图表解释和正式产物则会启用更完整的检查。

## 四、Skill 模块化设计

目前项目有 **11 个 Skill 模块和一份共享规则**。Skill 是可组合的能力模块，Agent 是执行这些能力的角色，两者不是一一对应关系。

| Skill | 主要作用 |
| --- | --- |
| `medical-research-assistant` | 理解科研学习目标，路由论文、方法、读图和汇报任务 |
| `medical-paper-guide` | 按论文顺序组织带读和阅读进度 |
| `medical-evidence-chain` | 连接研究问题、实验、结果、结论和来源 |
| `medical-method-tutor` | 解释研究方法、实验设计、对照和推理关系 |
| `medical-figure-tutor` | 解释图表、坐标、比较组、统计和视觉证据 |
| `medical-term-explainer` | 提供医学术语的中文解释和英文对应 |
| `medical-journal-club-ppt` | 组织论文汇报 PPT 和独立讲述提示 |
| `medical-research-plan` | 根据研究问题、条件和文献生成方案草案 |
| `medical-grounding-check` | 检查来源覆盖、无依据主张和证据绑定 |
| `medical-novice-simulator` | 模拟新手试读，暴露理解断点 |
| `medical-learner-simulation` | 用于内部学习任务、表现比较和迁移评估 |

这些 Skill 放在 `skills/` 目录，每个模块有自己的 `SKILL.md` 和 `manifest.json`。模块提供角色职责、输入输出、证据规则和调度信息；共享规则负责统一来源、未知条件、输出结构和安全边界。

Skill 可以被其他宿主参考，但完整的 PDF 解析、图件处理、调度、存储、PPT/DOCX 导出和三 Agent 协作依赖主程序。

## 五、三条主线如何交叉闭环

论文带读、PPT 和研究方案不是三个互不相干的按钮。它们共享论文来源、材料版本、用户关注点和核验结果。

例如：

- 带读中发现用户对某个实验方法不理解，可以进入方法解释，再把理解重点带入 PPT；
- PPT 生成时使用的图件、图注和结果必须能够回到论文来源；
- 研究方案可以参考论文的设计思路，但必须把“论文已经得到的结果”和“新课题可能得到的结果”分开；
- 交叉复核会检查三类产物的背景、设计、对照、结果和局限是否一致；
- 如果论文更新、图件变化或方案修订，旧的通过结果会失效，需要重新核验。

内部主线流程会把至少两类实际产物和原始来源送入交叉复核，检查是否存在遗漏、矛盾、虚构引用或条件错配。没有生成的产物不会被伪造为已完成。

## 六、学习闭环与迁移能力

项目内部还设计了从“讲懂”到“会迁移”的流程。模拟新手先根据教学产物完成一个汇报或研究设计任务，核验角色找出具体断点，导师进行针对性补教；随后换一个人群、资源、时间或结局条件，让新手独立处理新情境。

例如：论文研究的是住院患者的随机试验，迁移任务可能换成一次性体检数据，要求判断哪些设计思路仍然有用、哪些结论不能直接套用。这个阶段重点检查用户是否理解了研究逻辑，而不是是否背下论文数字。

小样本适合快速定位具体问题，完整论文和跨功能产物适合检查整体连贯性。内部审核会比用户最终看到的交付更严格；轻微措辞问题可以后续优化，但来源错误、关键条件丢失、图件错绑和实质性结论错误必须阻断。

## 七、前后端和运行结构

### 前端

前端使用 React 和 Vite，主要负责：

- 工作区和论文列表；
- 对话式带读界面；
- Markdown 结构化渲染；
- PDF 页面、图件和原文对照；
- PPT 与研究方案生成专区；
- 设置、阅读进度和导出入口。

### 后端

后端使用 Express 和 TypeScript，主要负责：

- PDF 导入、文本和页面解析；
- 图件注册、原图保存和显示资源；
- 模型调用和结构化输出；
- Agent 调度、预算、取消、缓存和恢复；
- 论文、对话、阅读进度和生成版本的本地持久化；
- PPTX、DOCX 和 Markdown 导出；
- 来源核验、跨功能复核和内部学习闭环。

浏览器只和本地服务通信，模型密钥由后端进程读取，不发送到前端。默认是本机单用户应用，数据目录、导出目录和运行记录不会进入 Git。

## 八、模型和部署方式

项目支持两类运行路径：

1. 使用本机已安装并登录的 Codex CLI；
2. 使用显式配置的兼容 Chat Completions API。

兼容 API 路径不要求原生 Codex 订阅额度，使用哪一家服务就由哪一家服务计费。模型能力会影响图表解释、长文本处理和结构化输出质量，尤其是 PPT 中的原图理解需要支持图像输入的模型。

用户安装项目后通常需要 Node.js 22.13+、安装依赖、配置模型并启动本地服务。这是常见开源 Agent 项目的使用方式；会使用 Codex、Claude Code、Cursor 等工具的人，可以直接让 Agent 阅读 README 并完成部署。

## 十、后续可以一起做什么

如果继续合作，比较适合从以下方向推进：

- 用不同医学论文做真实带读、PPT 和研究方案走查；
- 检查新手是否真的能理解图表和实验设计；
- 优化 PPT 的视觉层次、图文关系和汇报节奏；
- 增加医学领域的专门 Skill，例如影像、组学、临床观察或动物实验；
- 用更多小样本和完整论文测试迁移能力；
- 根据真实使用反馈调整调度器何时启用完整三 Agent 链路；
- 继续改善安装、模型配置和错误恢复体验。

整个项目的核心判断标准不是“生成了多少文字”，而是用户是否更清楚地理解了问题、证据、实验设计和下一步，以及生成的 PPT 和研究方案能不能经得起来源核对和导师讨论。
