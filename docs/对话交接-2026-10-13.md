## 3. 对话中表达过的产品想法与偏好

这一节帮助新会话理解作者，而不是给作者定型。它合并了反复出现的倾向，并注明几处后期改变；未提到的细节不应据此替作者作永久决定。

### 3.1 教学体验

1. 面向医学及医学相关科研新手，典型用户是刚进课题组的本科生，也包括起步阶段研究生。不要无故扩展到泛学科万能助手。
2. 先讲背景、目的、价值和整体思路，再大致顺着论文推进，关键实验展开。不是一上来逐字翻译，也不是只给一页摘要。
3. 讲清“为什么做—怎么设计—测了什么—对照是什么—结果怎样—支持什么结论”。逐渐帮助用户理解实验设计、分析结果、产生课题想法。
4. 图表初次出现时多解释类型、横纵轴、组别、图例和读法；后面遇到熟悉类型，减少重复基础教学，更关注这篇论文的数据和意义。
5. 术语关键处中英对照。方法先讲原理、测量对象、用途和对照，不默认展开成详细实验操作培训。
6. 讲解充分但有节奏。允许长回答，也允许分段；靠小标题、短段落和清楚的逻辑改善阅读，不机械规定长短，不堆大段无层次文字。
7. 允许随时追问、延伸讨论；偏离后及时收住，提醒是否接回主线。用户可以知道现在读到哪里、接下来读什么。
8. 支持像 Codex 一样选中回答中的句子再提问，也需要 PDF、原文、图表对照及局部查看。
9. 轻量记住已讲内容和用户熟悉度，不反复把用户当作完全不懂，也不把“讲过”当作“已经掌握”。练习可选，不强制考试。
10. 结尾可以在对话里总结论文。当前也可直接要求整篇概览、实验思路总结或汇报式总结，不必先精读完；不是另一个独立摘要模块。

### 3.2 PPT 和研究方案

1. PPT 是真正用于展示的幻灯片：需要图文布局、视觉层级、留白和适度设计，不能只把大段文本排成整齐方块。可借鉴优秀实现，但以医学证据表达为中心。
2. 汇报常用结构包括背景、实验设计、证据与结果、创新与不足、课题启发。讲述提示单独提供，不能塞进幻灯片正文。
3. PPT 可直接选择或导入论文生成，不要求先完成带读。页数等少量选项应容易操作，其余让系统合理处理。
4. 方案可从老师给的方向、个人灵感或已有问题开始；输入研究目标、资源、限制，可选一篇或多篇参考论文，必要时联网补充。
5. 方案是用于和导师讨论的完整草案。研究问题、依据、分组、对照、终点、条件和可行性要清楚，不能只给几个想法。
6. 早期用户希望生成后自行用外部软件编辑；后来的明确补充是应用内也要能修改要求、取消、重试和保留版本。以后一版决定为准，同时保持界面简洁。

### 3.3 界面和使用感受

1. 本地电脑使用为主，风格偏 iOS 与 Codex 的清爽组合。重视美观、字体统一、合理间距，既不要拥挤，也不要过度留白。
2. 左侧承担新建、导入、列表、搜索、课题分组、重命名和归档；右侧承担当前内容、参数、生成、修改、版本和导出。三专区有各自列表。
3. 同一论文可做多份 PPT；一份方案可参考多篇论文。保留来源对应关系，不把所有成果强制挂在一篇论文下面。
4. 日常先归档，设置中恢复或彻底删除。取消后保留要求并可编辑重试；不必增加“清空一切”，新建即可重新开始。
5. 已有成果要保存实际使用的来源及图片副本。删原论文不能连带损坏成果查看、修改或导出。
6. 早期不希望扩张成大型笔记系统；现有轻量笔记、复制等能力可保留，不把笔记变成主线。
7. 新安装默认空白论文库。实际导入的论文应保留，不能把它们误当示例清理。

### 3.4 质量、写作和协作方式

1. 抓大放小，先稳定常见操作。用户所说“90% 常见情况可用”是目标，不是已测得的成功率。
2. 反对靠省掉重要核验投机提速；倾向于先把 Skill 打磨好，再减少普通交付中不必要的反复打回。
3. 不喜欢防御性写作：次要后台意见不要变成用户正文里的警告、反复声明和自我解释。重要局限仍要在相关位置自然讲清一次。
4. 可以联网、找论文、查资料及参考 GitHub；检索要服务当前任务并及时收敛，不人为把常见操作限定成困难的离线挑战。
5. 希望开发 Agent 自主完成已授权工作，少反复问确认、少停在计划上。遇到卡点要解释原因并推进可做部分，不虚报完成。
6. “开发时少开子 Agent 节省额度”不等于削减产品内部三 Agent 协作。当前未要求新开开发子 Agent。
7. 重视原创设计表达，不希望介绍写成“到处拼抄”。应讲清自主设计、组合和打磨成果，同时保留实际第三方许可证与必要署名。
8. 给同学的介绍用自然、有条理的交流口吻；正式材料准确、完整、精炼，不刻意凑字数。文档少用满篇星号强调，适合用编号。
9. 新旧环境和新旧方案变化时要整体检查前端、后端、调度、Skill、存储与测试，不能只迁移表面功能。
10. 用户常把建议称为“提醒”或“宏观调控”，希望开发者批判判断，不要机械落实每个随口想法。曾鼓励充分自主迭代，同时关注单次成本；这不是无限预算承诺。
11. 2026-10-14用户明确要求每轮内部迭代完成后“先锐评，再继续”。开发 Agent 基于本轮真实运行记录与成品，先评价新增覆盖、失败与未验收项、修复证据、功能投入是否均衡、耗时与用量，再据此调整下一轮；在已经授权的范围和预算内继续，不把复盘变成每轮等待确认。

## 4. 架构与最重要的闭环

### 4.1 三 Agent + 调度器

| 部分 | 职责 |
| --- | --- |
| 导师 Agent | 面向用户组织讲解、生成 PPT/方案，根据反馈补教与修订；可称主 Agent |
| 新手模拟 Agent | 独立尝试理解、复述、汇报和设计，暴露真实学习断点；不提前读取核验答案 |
| 来源核验 Agent | 对照原始材料检查事实、图表、引用、实验条件和结论；核验意见也要有依据 |
| 调度器 | 决定路径、依赖、预算、角色可见材料、版本、缓存、取消、恢复和发布条件 |

旧表述里出现过“新手兼来源检查”“修订核验 Agent”等命名。当前源码和公开说明应统一为上表；修订是导师职责，不凭旧措辞另造第四个角色。

完整教学路径可概括为：导师生成 → 新手试读 → 来源核验 → 定位断点 → 导师有界修订 → 新手复读与来源复核。普通问答按任务选择必要阶段，不是每次固定走完整链。

### 4.2 反复强调的三功能交叉

内部迭代不仅分别检查带读、PPT 和方案，还把它们作为相互检验的材料：

1. 带读形成证据链，PPT 检查能否压缩成可讲述的汇报，方案检查能否把思路转成新的实验设计。
2. 模拟新手拿着 PPT 讲，检验页面是否表达清楚、带读是否教到了；也可以借助学到的方法提出方案，检验对照和推理能力。
3. 核验同时看产物与原论文：三者的背景、组别、结果方向、局限和来源是否一致；PPT 精简是否漏掉关键条件；方案是否把假设误当事实。
4. 导师针对断点补教，新手修正，再更换人群、资源、时间或结局条件验证迁移，避免只会背原论文。
5. 产物或来源更新后，旧核验不能继续作通过证明。三份东西彼此说法一致，也不能替代对原文的检查。

关键入口：`scripts/three-mainlines.ts`、`server/cross-function-review.ts`、`server/cross-function-sources.ts`、`server/learning-closure.ts`、`server/closure-product-gate.ts`。交叉核验接口至少需要两类真实产物；完整三产品验收另有三类产物及导出要求。

完整交叉与迁移实验属于内部迭代机制，不意味着每个用户请求都同时生成三类产物。模拟学习结果用于比较候选 Skill，不直接代表真人学习效果。

### 4.3 11 个 Skill 与共享规则

模块化使教学规则可单独改动、复用和测试，减少每次修改整个 Agent 的开发及回归成本。Skill 与 Agent 不一一对应；一个任务可组合多个模块，同一个模块也可服务多条主线。

| Skill 目录 | 主要作用 |
| --- | --- |
| `medical-research-assistant` | 学习任务路由、基础解释与主助手组织 |
| `medical-paper-guide` | 顺序带读与阅读节奏 |
| `medical-evidence-chain` | 问题、实验、证据与结论的连接 |
| `medical-method-tutor` | 方法原理、测量对象、实验设计与对照 |
| `medical-figure-tutor` | 图表读法、组别、数据与视觉证据 |
| `medical-term-explainer` | 中英术语与必要概念 |
| `medical-journal-club-ppt` | 医学汇报结构、幻灯片与独立讲述提示 |
| `medical-research-plan` | 研究问题、约束、设计与方案生成 |
| `medical-grounding-check` | 来源、事实与证据绑定核验 |
| `medical-novice-simulator` | 模拟新手试读、提问与理解断点 |
| `medical-learner-simulation` | 开发验证中的学习模拟 |

共享规则在 `skills/shared/rules.md`。模块有 `SKILL.md` 和 `manifest.json`。复制 Skill 可复用教学指令；PDF 处理、图件、联网、调度、持久化和导出由宿主程序提供。这里的迭代主要改 Skill、提示词、样本与协作流程，不是模型权重训练。

## 5. 前后端和模型接入

1. 前端：React / TypeScript / Vite。主工作区是 `app/research-workspace.tsx`，PDF 阅读与框选在 `app/research-pdf.tsx`，生成专区在 `app/generation-zones.tsx`。`/assistant` 与 `/prototype` 是旧入口，不代表当前默认产品。
2. 后端：Express / TypeScript。`server/index.ts` 提供接口；`orchestrator.ts`、`scheduler.ts` 等组织任务；PDF、图件、检索、来源、方案、导出和生命周期各有模块。
3. 持久化：后端本地文件保存材料、会话、任务、成果与版本；部分未提交输入和阅读状态在浏览器中。因此清后端文件不等于清前端状态，换数据目录也不等于界面必然全新。
4. 导出：PPTX、独立讲述提示、方案 DOCX/Markdown。成果来源副本需和生成、删除、恢复逻辑一起维护。

| 模型路径 | 含义 |
| --- | --- |
| `codex` | 使用已安装并登录的 Codex CLI |
| `codex-configured` | 使用 CLI 中显式配置的提供方、模型和 API Key 认证；当前本地使用此路径 |
| `compatible` | 后端直接调用兼容 Chat Completions 的服务，不要求 Codex CLI 或原生订阅额度 |

开发时使用 Codex，不代表应用只能在原生 Codex 上运行。用户可以让自己的开发 Agent 帮忙安装、配置 API；能否用某平台额度，取决于该平台是否提供可调用接口，不能自动借用任意聊天会员。图像、结构化输出和具体模型稳定性需要实际验证，不能把通用接口等同于所有国产模型均已测通。

旧内部脚本也要逐个检查模型入口，不能只改在线服务。`scripts/replay.ts` 已通过 `c884b69` 改为统一提供方入口；旧交接关于它仍写死 Codex 的说法已过时。

## 6. 在线交付与内部严格迭代

这是最近一轮最重要的确定项：

1. 在线：只要没有影响主要理解、事实和设计的重大问题，优先给出可用成果。次要措辞、解释粒度等意见保留内部，默认不提示用户，也不因数量多就整轮打回。
2. 重大错误：虚构来源或图件、数字/方向错误、假设写成结果、决定性对照缺失、关键可行性条件缺失等，仍要修复或阻断。“材料缺失声明”不是放行重大问题的理由。
3. 用户正文：不附审核清单、角色评语、内部编号；必要科学条件和论文局限在相关位置正常讲。用户追问可靠性时，按当前版本解释依据。
4. 内部：继续完整记录问题、复验、跨功能与迁移表现，不放宽评分、晋级或发布门槛。并行与缓存可以研究，但不能破坏角色独立作答和前后依赖。
5. 提速：优先减少重复工作、改进初稿和局部修订。不能把模型失败改成假成功，不能把来源变化后的旧缓存继续当有效结果。
6. 失败恢复：仅在确认失败、没有输出且预算允许时有界重试；结果未知、取消、认证错误不能一概重发。已有输入、版本和实际调用记录要保留。
